# 监控编排使用说明（Prometheus + Grafana）

## 1. 组件与端口

| 组件 | 端口 | 作用 |
| --- | --- | --- |
| Prometheus | 9090 | 指标抓取、规则评估、告警推送 |
| Alertmanager | 9093 | 告警分级路由、去重、静默 |
| Grafana | 3000 | 可视化大盘（默认 admin/admin） |
| redis_exporter | 9121 | Redis 指标（内存/连接/从节点/主从切换） |
| kafka_exporter | 9308 | Kafka 指标（消费积压、ISR、topic 吞吐） |

## 2. 一键启动

```bash
# 前提：业务服务已通过 scripts/mall.sh start 在宿主机启动（:8081/:8082/:8083/:8080）
docker compose -f docker-compose-monitoring.yml up -d

# 查看状态
docker compose -f docker-compose-monitoring.yml ps

# 停止（保留数据卷）
docker compose -f docker-compose-monitoring.yml down
```

访问：
- Grafana <http://localhost:3000>（首次 admin/admin，dashboard 自动加载「Mall Coupon Platform - Overview」）
- Prometheus <http://localhost:9090>（Status → Targets 可看抓取健康）
- Alertmanager <http://localhost:9093>（Alerts 页看当前告警）

## 3. 抓取目标与网络

业务服务跑在宿主机，容器通过 `host.docker.internal` 访问（compose 里已配 `extra_hosts: host.docker.internal:host-gateway`）。抓取配置在 `monitoring/prometheus/prometheus.yml`：

- `mall-services`：coupon 8081 / seckill 8082 / order 8083，路径 `/actuator/prometheus`，并打 `app` 标签
- `mall-gateway-health`：网关 8080，路径 `/actuator/prometheus`（依然关闭 `/actuator/gateway` 防止无鉴权篡改路由）
- `redis` / `kafka`：exporter 容器，走 compose 内部网络（`kafka-exporter` 默认连 `host.docker.internal:9095` 的 `HOST_DOCKER` 监听器）

**如果把业务服务也容器化并接入同一网络**：把 prometheus.yml 里的 `host.docker.internal:808X` 改成服务名（如 `mall-coupon-service:8081`），删除 `extra_hosts` 即可。

**HA 环境**：Redis 哨兵下 exporter 要连主库/从库地址，通过环境变量 `REDIS_EXPORTER_ADDR` 覆盖，例如 `REDIS_EXPORTER_ADDR=mall-ha-redis-slave:6379 REDIS_PASSWORD=xxx docker compose ...`。

## 4. 指标来源（与后端一致）

业务指标由 `BusinessMetrics` 暴露，Micrometer 的 `.` 在 Prometheus 里转成 `_`：

| 后端 Counter/Timer | Prometheus 指标名 |
| --- | --- |
| `mall.seckill.success.total` | `mall_seckill_success_total` |
| `mall.seckill.soldout.total` | `mall_seckill_soldout_total` |
| `mall.seckill.rejected.total` | `mall_seckill_rejected_total` |
| `mall.coupon.claim.success.total` | `mall_coupon_claim_success_total` |
| `mall.seckill.latency` | `mall_seckill_latency_seconds_bucket` |

标准指标：`http_server_requests_seconds_*`（QPS/P99/5xx）、`jvm_*`（堆/GC）、`up`（存活）。

## 5. 告警规则

规则文件 `monitoring/prometheus/rules/mall-alerts.yml`（挂载到 `/etc/prometheus/rules/`），分三组：

- **服务可用性**：ServiceDown（critical）、HighErrorRate、HighLatencyP99
- **业务异常**：SeckillSoldOutSpike、SeckillLatencyHigh、CouponClaimStalled
- **中间件**：Redis 从节点、Kafka 消费积压、Kafka ISR 收缩

Alertmanager（`monitoring/alertmanager/alertmanager.yml`）按 severity 分级，critical 30 分钟重复、warning 4 小时；`ServiceDown` 会抑制同实例其他告警（防风暴）。**本地默认 receiver 是空 webhook**（告警只在 UI 显示），生产需替换为真实 webhook（企业微信/钉钉/PagerDuty）。

## 6. 前端管理台联动

前端（`web/`）的「监控中心」页会探测 3000/9090/9093 的可达性并提供直达链接，与这套编排配套。

## 7. 常见问题

- **Targets 全 DOWN**：业务服务没启动，或 `host.docker.internal` 解析失败（Linux 需确认 compose 版本支持 `host-gateway`）。
- **Dashboard 无数据**：确认服务已暴露 `/actuator/prometheus`（网关刻意不暴露），且 Prometheus Status → Targets 为 UP。
- **Redis 从节点数告警**：单机 demo 无从节点属正常，规则已标为 info 级。
- **改配置后**：Prometheus 支持热加载 `curl -X POST http://localhost:9090/-/reload`；Grafana provisioning 每 30 秒自动同步。
