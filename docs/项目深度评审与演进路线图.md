# 优惠券与秒杀平台项目评审

评审日期为 2026-11-25。后端以工作区的 `e0e2ce4` 为基线，前端以当时的工作区为准，包含 5 个已有修改。本文依据代码、测试、TLA+ 模型和仓库历史压测报告。以下故障窗口来自代码走读，尚待跨服务故障注入验证。

## 项目值得做深的地方

把主线定为「高并发抢购的库存一致性，以及订单用券的可靠结算」。Redis Lua 原子完成库存和资格校验，Kafka 分担落库压力，订单和券分别用数据库条件更新推进状态。券在领取时存下规则快照，订单服务按同一套规则复算实付，再完成绑定。沿着这条链路，可以验证请求受理后会不会丢、支付后券能否核销，以及修复任务会不会制造新的不一致。[领取批处理](../mall-coupon-service/src/main/java/com/mall/coupon/consumer/CouponClaimConsumer.java#L76) · [订单绑定与复算](../mall-order-service/src/main/java/com/mall/order/service/impl/OrderServiceImpl.java#L195) · [结算单状态推进](../mall-coupon-service/src/main/java/com/mall/coupon/service/impl/CouponSettlementServiceImpl.java#L233)

## 优先修复的业务风险

### P0 在线对账会覆盖领券请求写入的数据

对账先扫描 token，再读取 MySQL 发券数，然后覆盖 Redis 库存、删除限领 Hash、重新写入限领计数。模板锁只协调使用这把锁的代码，领券 Lua 不获取该锁。对账通过 token 检查后，领券仍可成功预扣。若此时对账按旧快照写回，预扣可能被覆盖。删除 Hash 到重建完成之间，请求还可能读到空的限领计数。单库下模板计数有总量条件更新兜底，但每用户限领和已受理请求的最终结果仍有风险。库存数相等时对账提前返回，也会跳过单独的限领计数漂移。[对账实现](../mall-coupon-service/src/main/java/com/mall/coupon/job/CouponStockReconcileJob.java#L61) · [领券 Lua](../mall-common/src/main/resources/lua/coupon_claim.lua#L10) · [数据库库存上限](../mall-coupon-service/src/main/java/com/mall/coupon/mapper/CouponTemplateMapper.java#L20)

扫描只看 token 键是否存在，已落库的 `CONSUMED` 标记也会让整个模板跳过对账。活动持续有成功领券时，这种标记可在多轮扫描期间始终存在。验收时应把真正的在途预占、已提交结果和可对账的差异区分开。[扫描条件](../mall-coupon-service/src/main/java/com/mall/coupon/job/CouponStockReconcileJob.java#L121) · [消费凭证写回](../mall-coupon-service/src/main/java/com/mall/coupon/consumer/CouponClaimConsumer.java#L137)

先把在线对账改为发现、记录和告警。自动修复须让领券入口和修复程序共享一个明确的协议。第一版可用短时维护状态阻止新预占，在途预占清零后重算，再用 Lua 在预期版本下切换库存与限领计数。把每用户已发券计数留在数据库作为最终校验时，需要与发券写入用同一事务，并评估额外写压力。验收要求对账与领券并发时，每人限领和模板总量都成立，即使库存数相等也能发现限领计数漂移。

### P0 秒杀预扣成功后可能缺少可恢复记录

秒杀 Lua 先扣库存并写已购 Set，Java 随后生成订单 ID、写 token，再发 Kafka。进程如果在预扣后、发消息前停止，异常处理分支不会执行。token 尚未写入的预占没有逐笔标识，token 已写入时也没有独立的到期处理程序消费它。消费端的过期补偿需要先收到消息，订单超时扫描只覆盖已有订单。结果可能是少卖，并且该用户无法在活动剩余时间重试。[秒杀入口](../mall-seckill-service/src/main/java/com/mall/seckill/service/impl/SeckillServiceImpl.java#L73) · [Lua 扣减](../mall-common/src/main/resources/lua/seckill.lua#L23) · [消费端补偿入口](../mall-order-service/src/main/java/com/mall/order/service/impl/OrderServiceImpl.java#L53) · [超时扫描](../mall-order-service/src/main/java/com/mall/order/consumer/OrderTimeoutConsumer.java#L57)

让一次 Lua 原子写入预扣、预占 ID、所属桶和可扫描的到期记录。让消费者认领和超时回收争用同一条状态记录。回收先胜出时，迟到消息须拒绝建单。若消费者先认领后退出，恢复程序需确认订单是否已落库，并用持久化的状态约束旧消费者与接管任务的并发写入。相同请求 ID 重试应能查询已有结果。先用现有 Redis 架构验证进程重启后的恢复，再根据故障目标验证 Redis 主从切换时的持久性。验收要求每个已受理 ID 在依赖恢复后都有可查询的终态，旧预占的补偿不得清掉同一用户后续的新预占。

### P1 订单事件与销量更新有两层双写窗口

支付先提交订单状态，再异步发支付事件。建单通过 `afterCommit` 发销量事件。关单在标记库存已归还之后发布取消事件。三条路径均缺少与自身业务状态同事务写入的待投递记录，发送方法也未处理异步完成结果。现有券巡检能在部分场景重新核对订单状态，但过程有延时。销量消费也有独立窗口：先写 Redis 的事件幂等状态，再改 MySQL 的 `sold_count`。数据库更新失败时，Kafka 重投可能因 Redis 已记录该事件而跳过写库。[支付及发送](../mall-order-service/src/main/java/com/mall/order/service/impl/OrderServiceImpl.java#L153) · [关单发送](../mall-order-service/src/main/java/com/mall/order/service/impl/OrderServiceImpl.java#L331) · [建单提交后发送](../mall-order-service/src/main/java/com/mall/order/service/impl/OrderServiceImpl.java#L395) · [销量消费者](../mall-seckill-service/src/main/java/com/mall/seckill/consumer/SeckillSoldConsumer.java#L68)

订单侧先用事务 Outbox 覆盖支付事件，再扩展到建单和取消。订单状态和事件一起提交，发布器收到确认后更新投递状态。发布器在确认后退出仍可能重投，消费端应以事件 ID 去重，去重记录与数据库副作用同事务。若保留异步销量投影，定义它等于活动中有效订单的数量，按订单维护可恢复的投影状态，并处理建单和取消跨 topic 乱序。先用有界重试、积压指标和可审计的重放跑通，再决定轮询发布器是否需要升级为 CDC。Kafka 的事务可以覆盖 Kafka topic 与消费位移，外部 MySQL 的副作用需要外部存储参与保证。[AWS 事务 Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) · [Kafka 投递语义](https://kafka.apache.org/43/design/design/)

### P1 支付与巡检的边界需要成为产品规则

支付 SQL 只检查待支付状态。超过 15 分钟且关单任务尚未处理时，支付仍可成功；应决定支付截止时间是否是硬约束，并使 SQL、接口和页面按同一规则判断。券巡检反复取最旧的一批到期锁券记录。如果最前面一批都暂时无法处理，例如订单服务查询一直失败，后面的记录会跨轮被挡住。加稳定的 `(lock_time, id)` 游标或按 `next_retry_at` 取任务，记录最老待处理时间。前端取消订单后直接提示「库存已归还」，而后端允许库存由后台补偿，页面应以归还状态反馈。[支付条件](../mall-order-service/src/main/java/com/mall/order/mapper/SeckillOrderMapper.java#L32) · [券巡检](../mall-coupon-service/src/main/java/com/mall/coupon/service/impl/CouponSettlementServiceImpl.java#L161) · [批次排序](../mall-coupon-service/src/main/java/com/mall/coupon/mapper/CouponSettlementMapper.java#L43) · [前端提示](../web/src/views/OrdersView.vue#L128)

### 把 TLA+ 模型对齐到真实写入步骤

当前两个模型把库存预扣和写 token 合在一个动作里，券对账也建模为无在途请求时的一次原子更新。秒杀建单的模型动作将销量事件一次性放入队列。代码中的 Redis、MySQL 和 Kafka 操作由多个步骤组成，模型省略了这次评审找到的交错。建议先拆分预扣、凭证落地、订单提交、事件持久化和发布，再逐个加宕机、消息重复、超时和重试。保留库存守恒、限领、券与结算单一致等安全属性，另在依赖恢复且任务得到调度的假设下检查终态可达。仓库三个模型仍需通过 `verify-tla`。[领券模型](../formal/models/CouponLifecycle.tla#L43) · [券对账模型](../formal/models/CouponLifecycle.tla#L102) · [秒杀模型](../formal/models/SeckillProtocol.tla#L45) · [建单动作](../formal/models/SeckillProtocol.tla#L89)

现有 IT 已覆盖 MySQL、Redis 上的关单后再买以及销量乱序处理。下一批放 GitHub Actions 的容器集成测试，至少验证下表。现有测试可以保留为单服务回归，新增场景需要在关键调用之间能暂停或注入失败，并用数据库终态断言跨服务结果。[订单 IT](../mall-order-service/src/test/java/com/mall/order/OrderServiceIntegrationIT.java#L86) · [销量 IT](../mall-seckill-service/src/test/java/com/mall/seckill/SeckillSoldIntegrationIT.java#L80) · [CI 集成测试](../.github/workflows/ci.yml#L46)

| 故障场景 | 验收结果 |
| --- | --- |
| 对账查询快照时同时领券，对账 Hash 重建时再次领券 | 每人领券数不超过限额，模板发券数不超过总量，受理请求全部有终态 |
| Redis 预扣后进程退出，或 Kafka 发出后确认超时再重投 | 同一预占最多落单一次，未落单的预占最终归还，重复补偿不会改动新订单 |
| 支付提交后进程退出，发布器收到确认后退出 | 发布可恢复，订单保持已支付，绑定券仅核销一次 |
| 销量数据库更新失败、取消先于创建到达、事件重复 | 恢复后销量与有效订单数一致 |
| 自动关单与支付同时执行，或最旧锁券批次持续失败 | 每笔订单只有一个终态，后续可处理的券不会被首批阻塞 |

### 用热点实验决定是否改 Redis 分片

秒杀同一活动的 16 个库存 key 都用 `{activityId}`，整个 Lua 调用还会读活动状态和已购用户 Set，因此同活动由一个 slot 所在主节点执行。当前分桶设计保留了原子性和借桶能力。README 中的「打散 Redis Cluster 热点」应限定到不同活动。先对照单热点活动与多活动，测 Redis CPU、Lua 延迟和每组业务吞吐。若单热点达到瓶颈，再评估独立分片配额、用户固定路由和剩余库存再分配，明确容量收益和尾库存利用率的代价。[Redis key](../mall-common/src/main/java/com/mall/common/constants/RedisKey.java#L53) · [README 描述](../README.md#L234) · [Redis Cluster hash tag](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/#hash-tags)

## 面试怎么讲

现在就能讲清的开场是「我做了一个优惠券与秒杀平台。秒杀请求先用 Redis Lua 校验资格并预扣，再经 Kafka 异步落单。订单用券分为绑定时锁券和支付后核销。复盘代码时我发现，最麻烦的故障发生在两个系统各自成功的间隙，例如 MySQL 已支付、Kafka 事件还没发出去。我把这些窗口列出来，能指出现有补偿会覆盖哪些场景，以及哪些还需要持久化恢复记录。」

| 追问 | 讲述线索 |
| --- | --- |
| Kafka 重投怎样避免重复落单？ | 讲 Redis token 的工作状态、数据库活跃订单唯一索引，再说明 token 过期及补偿的边界。 |
| 锁券成功但订单写入失败怎么办？ | 讲订单待支付的条件更新、主动解锁和巡检查询订单终态。解释支付与关单争用时由哪个条件更新决定胜负。 |
| 为什么采用 Outbox？ | 指出数据库提交和发送之间的故障窗口。实现后用一次真实的重启恢复演示，再说明发布器重投为何仍需要消费者幂等。 |
| 3269 QPS 代表什么？ | 先报实验的成功、拒绝与网络错误，再解释约 490 笔成功响应/秒是怎么从原始数据算出来的。新实验再补最终落单率。 |

上线前后数字使用同一套负载和统计口径。面试时最有说服力的材料是一组有原始请求 ID、日志和数据库终态的故障实验，能说清某次失败怎样发生、怎样恢复、恢复花了多久。
